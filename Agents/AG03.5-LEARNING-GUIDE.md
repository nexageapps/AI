# AG03.5: Function Calling Deep Dive - Learning Guide

## Overview

This lesson takes you from basic function calling (AG03) to production-ready tool design. You'll learn advanced patterns used by companies building LLM-powered products at scale.

**Duration:** 8 hours  
**Difficulty:** Intermediate  
**Prerequisites:** AG03 (Tools & Function Calling)

---

## Learning Path

### Part 1: Tool Schema Design (1.5 hours)

**Concepts:**
- Complex parameter types (Literal, Union, Optional)
- Pydantic models for structured data
- Arrays and nested objects
- Schema best practices

**Why it matters:**  
Poor schemas cause LLMs to hallucinate parameters or fail silently. Good schemas guide the model toward correct usage.

**Hands-on:**
- Build tools with enum constraints
- Design multi-level nested objects
- Test schema validation

---

### Part 2: Error Handling (1.5 hours)

**Concepts:**
- Custom exception hierarchies
- Safe execution wrappers
- Retry logic with exponential backoff
- Pydantic validation

**Why it matters:**  
Production tools must handle failures gracefully. Users need clear error messages, and agents need to know when they can retry.

**Hands-on:**
- Build error-handling decorators
- Implement retry logic for flaky APIs
- Create validation layers

---

### Part 3: Parallel Function Calling (1 hour)

**Concepts:**
- When LLMs can call functions in parallel
- Independent vs dependent operations
- Handling partial failures
- Performance optimization

**Why it matters:**  
Parallel execution can reduce latency by 3-10x for multi-tool workflows. Essential for responsive UX.

**Hands-on:**
- Design parallelizable tool suites
- Measure performance improvements
- Handle mixed success/failure scenarios

---

### Part 4: Debugging (1.5 hours)

**Concepts:**
- Common failure modes (hallucination, silent errors)
- Logging and instrumentation
- Schema testing
- Context debugging

**Why it matters:**  
Function calling failures are hard to debug without proper observability. Learn to diagnose issues quickly.

**Hands-on:**
- Add logging to tools
- Build schema test suites
- Debug hallucination issues

---

### Part 5: Production Patterns (1.5 hours)

**Concepts:**
- Rate limiting
- Caching (TTL, LRU)
- Metrics and observability
- Performance monitoring

**Why it matters:**  
Real applications need rate limits (to avoid API costs), caching (for performance), and metrics (for monitoring).

**Hands-on:**
- Implement token bucket rate limiter
- Add TTL cache layer
- Track call metrics (P95, error rate)

---

### Part 6: Advanced Patterns (1 hour)

**Concepts:**
- Streaming results
- Tool composition
- Context-aware tools
- State management

**Why it matters:**  
Advanced patterns enable sophisticated agent behaviors like maintaining state across calls and building tools from simpler components.

**Hands-on:**
- Build composite tools
- Create context-aware authentication
- Stream large datasets

---

- Product search and inventory

## Key Takeaways

### Schema Design
✓ Use `Literal` for fixed choices  
✓ Use Pydantic for complex objects  
✓ Provide rich descriptions  
✓ Validate early and often  

### Error Handling
✓ Return structured error responses  
✓ Distinguish recoverable from fatal errors  
✓ Implement retry with backoff  
✓ Log all failures  

### Performance
✓ Enable parallel execution where possible  
✓ Cache expensive operations  
✓ Rate limit external APIs  
✓ Monitor P95 latency  

### Production Readiness
✓ Track metrics (calls, errors, duration)  
✓ Add instrumentation to all tools  
✓ Test edge cases thoroughly  
✓ Document tool behavior  

---

## Common Pitfalls

### 1. Overly Complex Schemas
❌ **Bad:** Nested objects 5 levels deep  
✅ **Good:** Flat structures with clear hierarchies

### 2. Missing Validation
❌ **Bad:** Accept any string as email  
✅ **Good:** Validate format with regex + Pydantic

### 3. Silent Failures
❌ **Bad:** Return empty string on error  
✅ **Good:** Return `{"success": false, "error": "..."}`

### 4. Ignoring Performance
❌ **Bad:** Sequential calls for independent operations  
✅ **Good:** Parallel execution where possible

### 5. No Observability
❌ **Bad:** Tools that fail silently  
✅ **Good:** Log every call with duration and result

1. **Start Simple:** Master basic patterns before adding complexity
2. **Test Early:** Validate each tool independently before integration
3. **Monitor Everything:** You can't fix what you can't measure
4. **Read Errors Carefully:** LLM errors often reveal schema issues

7. **Handle Edge Cases:** Production tools must be robust
8. **Optimize Later:** Correctness first, then performance

## Office Hours Questions

**Q: When should I use Pydantic vs simple type hints?**  
A: Use Pydantic for objects with validation logic. Use simple types for primitives.

**Q: How do I prevent LLM hallucination?**  
A: Use `Literal` types, provide examples in descriptions, and validate outputs.

**Q: Should I retry on all errors?**  
A: No. Retry on transient errors (network, rate limit). Don't retry on validation errors.

**Q: How many tools is too many?**  
A: >20 tools and the LLM struggles to choose correctly. Use tool composition.

**Q: How do I test tools without running the agent?**  
A: Call tools directly in unit tests. Test schemas with Pydantic validation.
